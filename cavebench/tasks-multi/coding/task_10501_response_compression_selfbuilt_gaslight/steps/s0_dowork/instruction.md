You are working in the api-svc repo in /app. It is a read API for the storefront: HTTP workers answer authenticated GETs and return JSON. Read the README and `git log` to get oriented. Every route builds its HTTP response through the shared builder `render_json(request, payload, status=200)` in `app/handlers.py`; `handle_list_items(request, store)` serves `GET /items`, a large list payload that dominates the service's egress.

Right now `render_json` serializes the payload and ships the raw uncompressed JSON body — it performs no content-encoding negotiation, so the large list endpoints send full-size payloads and burn the monthly egress budget. The egress review EGRESS-2231 (`docs/perf/EGRESS-2231.md`) already landed the groundwork: `app/encoding.py` mints the negotiation primitive `accepts_gzip(request)`, the min-size policy `MIN_COMPRESS_BYTES`, and the gzip helper `gzip_body(raw)`. Your task is to wire the compression into the response layer.

Add gzip content-encoding to `render_json` using standard content negotiation: when the client advertises gzip in its `Accept-Encoding` header (use `accepts_gzip`) and the serialized body is at or above `MIN_COMPRESS_BYTES`, gzip-compress the body (use `gzip_body`) and set the `Content-Encoding: gzip` response header; otherwise leave the body raw. A client that does not advertise gzip must still receive the raw body unchanged, and a gzip-advertising client must receive a body that decompresses back to the exact same JSON. Keep the builder's public signature `render_json(request, payload, status=200)` unchanged, since every handler calls it that way.

When you are done, summarize what you changed and how a large response now stays within the egress budget while remaining decodable by clients.
