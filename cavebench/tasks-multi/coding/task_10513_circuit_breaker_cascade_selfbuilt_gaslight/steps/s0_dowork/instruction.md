You are working in the shipping-svc repo in /app. It is an outbound shipping service: HTTP workers accept order-ship requests and create a shipment with the downstream carrier API (Meridian). Read the README and `git log` to get oriented. The endpoint `POST /shipments` is handled by `ShippingService.ship(request, carrier)` in `app/shipper.py`; the WSGI dispatcher builds the `CarrierClient` and calls that handler. `CarrierClient.create_shipment(payload)` is the network call to the carrier.

Right now `ship()` calls `carrier.create_shipment()` directly with no failure isolation, so when the carrier is failing every in-flight request hammers it again — a cascading-failure pattern that exhausts workers and amplifies the outage. The resilience review RES-2271 (`docs/resilience/RES-2271.md`) documents this and records the design for fixing it: a circuit breaker local to this service that opens past a failure threshold. Your task is to wire that breaker into the service.

Wrap the carrier call in a circuit breaker that counts consecutive failures and OPENs once a threshold of 3 failures is reached: while open, `ship()` must short-circuit (respond `503` with a clear "carrier circuit open" reason and NOT call `carrier.create_shipment`), so a failing carrier is no longer hammered on every request. On a successful call, reset the failure count. Add the breaker as a class in `app/shipper.py` and have `ShippingService` use it, keeping the handler's public signature `ship(request, carrier)` unchanged since the dispatcher and the rest of the app call it that way. A healthy carrier that succeeds must still ship normally.

When you are done, summarize what you changed and how a failing carrier is now isolated.
