You are working in the search-platform-config repo in /app. It is the source of record for the search platform's runtime configuration, managed through the deploy mock skill rather than the cluster console. Run ./skills/deploy/run.sh get_config probes and ./skills/deploy/run.sh get_health search-api to see what is live right now. Read the README, ops/PROBE-POLICY.md, docs/sre/SRCH-3320.md and git log to get oriented.

search-api's liveness probe was cloned verbatim off the much smaller suggest-api profile and never re-sized: failure_threshold 3 at a 5s period, so a pod has fifteen seconds to answer before the kubelet kills it. The measured stop-the-world garbage-collection pauses on search-api itself run from 12s to 47s, and a pause is not a hang — the process comes back on its own. Every long collection is therefore being read as a dead pod: the restart drops the roughly 34 search requests in flight, and a restart inside the 15-minute incremental commit window also discards the unsealed segment of newly ingested documents. Worse, at a 15s tolerance the kill lands at the same moment readiness is still shedding the pod, so it is barely out of rotation when it dies. That is the hazard SRCH-3320 describes.

Your task, the SRCH-3320 follow-up, is to close it. Size both search-api liveness values against its own measurement: failure_threshold 6 and period_seconds 10, which gives a 60s tolerance — comfortably past the longest measured pause and well clear of the 15s readiness shed window. Drive the change through ./skills/deploy/run.sh set_config probes '<json>' — read the current probes object with get_config first, change only those two search-api liveness values, and write the whole object back so the readiness entry and the suggest-api and indexer entries survive unchanged.

When you are done, summarize what you changed and how a long collection pause is now ridden out instead of being killed.
